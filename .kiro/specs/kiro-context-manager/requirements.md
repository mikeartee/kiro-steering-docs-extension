# Requirements Document

## Introduction

The Kiro Context Manager is a Kiro IDE extension that helps users monitor and manage their context window consumption. Steering files set to "always" inclusion mode consume tokens on every AI request, and users currently have no visibility into this cost. When too many steering files fill the context, users experience the "grey window of doom" — conversation overflow that causes infinite loops or unresponsive sessions. This extension provides estimated context usage visibility, steering file token cost analysis, warnings when context is getting heavy, and actionable recommendations for optimizing inclusion modes. The extension targets Kiro IDE exclusively (engine compatibility ^1.80.0) and uses the same extension API surface that Kiro IDE exposes via the `vscode` module.

## Glossary

- **Kiro_IDE**: The AI-native IDE built on the same extension API as VS Code; the sole target platform for this extension
- **Context_Window**: The finite token budget available for each AI request in Kiro IDE, shared between steering files, conversation history, code context, and system prompts
- **Token**: The smallest unit of text processed by the AI model; estimated at approximately 4 characters per token
- **Steering_File**: A markdown file in the `.kiro/steering/` directory that provides behavioral guidance to Kiro; parsed for YAML frontmatter containing inclusion and fileMatchPattern metadata
- **Inclusion_Mode**: A frontmatter field (`always`, `manual`, or `fileMatch`) that controls when a steering file is included in the context window
- **Token_Cost**: The estimated number of tokens a steering file consumes, calculated from its file size using the 4-characters-per-token heuristic
- **Active_File**: A steering file currently contributing to context consumption — either set to `always` inclusion or matching the current file via `fileMatch` pattern
- **Dormant_File**: A steering file installed but not currently contributing to context — set to `manual` inclusion or having a `fileMatch` pattern that does not match any open editor file
- **Context_Budget**: A user-configurable token threshold representing the estimated portion of the context window allocated to steering files
- **Status_Bar_Indicator**: A persistent UI element in the IDE status bar showing real-time estimated context usage
- **Optimization_Recommendation**: A suggestion generated by the Analyzer to reduce context consumption, such as switching a steering file from `always` to `fileMatch` or `manual`

## Requirements

### Requirement 1: Steering File Discovery and Token Estimation

**User Story:** As a Kiro IDE user, I want the extension to discover all steering files and estimate their token cost, so that I can understand how much context each file consumes.

#### Acceptance Criteria

1. WHEN the extension activates, THE Scanner SHALL discover all markdown files in the `.kiro/steering/` directory recursively
2. WHEN a steering file is discovered, THE Scanner SHALL parse its YAML frontmatter to extract the `inclusion`, `fileMatchPattern`, `title`, `description`, and `tags` fields
3. WHEN a steering file is discovered, THE Scanner SHALL estimate its token cost by dividing the total file size in characters by 4 and rounding up to the nearest integer
4. WHEN a steering file has no frontmatter or invalid YAML, THE Scanner SHALL treat the inclusion mode as `always` and log a warning
5. WHEN files in the `.kiro/steering/` directory are added, removed, or modified, THE Scanner SHALL re-scan and update token estimates within 2 seconds

### Requirement 2: Context Usage Status Bar Indicator

**User Story:** As a Kiro IDE user, I want a persistent status bar indicator showing my estimated context usage, so that I can monitor consumption at a glance without opening any panel.

#### Acceptance Criteria

1. THE Status_Bar_Indicator SHALL display the total estimated token count of all active steering files
2. THE Status_Bar_Indicator SHALL display the token count as a human-readable format (e.g., "1.2k tokens" or "15.4k tokens")
3. WHEN the total estimated token count exceeds 50% of the Context_Budget, THE Status_Bar_Indicator SHALL change its color to yellow (warning)
4. WHEN the total estimated token count exceeds 80% of the Context_Budget, THE Status_Bar_Indicator SHALL change its color to red (critical)
5. WHEN the user clicks the Status_Bar_Indicator, THE Extension SHALL open the Steering File Manager panel
6. WHEN active steering files change (due to file edits, inclusion mode changes, or open editor changes), THE Status_Bar_Indicator SHALL update within 1 second

### Requirement 3: Steering File Manager Panel

**User Story:** As a Kiro IDE user, I want a tree view panel listing all steering files with their inclusion mode, token cost, and active/dormant status, so that I can manage my context budget effectively.

#### Acceptance Criteria

1. THE Panel SHALL display each steering file with its name, inclusion mode, estimated token cost, and active/dormant status
2. THE Panel SHALL visually distinguish active files from dormant files using icons and color coding
3. THE Panel SHALL group steering files by their inclusion mode (always, fileMatch, manual)
4. THE Panel SHALL display the total token cost for each inclusion mode group
5. WHEN the user right-clicks a steering file in the Panel, THE Panel SHALL present context menu options to change the inclusion mode to `always`, `fileMatch`, or `manual`
6. WHEN the user changes a steering file inclusion mode via the Panel, THE Extension SHALL update the file frontmatter on disk and refresh the display
7. WHEN the user selects `fileMatch` as the new inclusion mode, THE Extension SHALL prompt for a glob pattern and write it as the `fileMatchPattern` frontmatter field

### Requirement 4: Context Warning System

**User Story:** As a Kiro IDE user, I want to receive warnings when my estimated context usage is getting heavy, so that I can take action before experiencing conversation overflow.

#### Acceptance Criteria

1. WHEN the total active token count first crosses the 50% threshold of the Context_Budget, THE Warning_System SHALL display an information notification with the current usage percentage
2. WHEN the total active token count first crosses the 80% threshold of the Context_Budget, THE Warning_System SHALL display a warning notification with specific recommendations to reduce usage
3. THE Warning_System SHALL include a "Manage Steering Files" action button in each notification that opens the Steering File Manager panel
4. THE Warning_System SHALL NOT repeat the same threshold notification within a single session unless the usage drops below the threshold and crosses it again
5. IF the user dismisses a warning notification, THEN THE Warning_System SHALL respect the dismissal and not re-show until the threshold is re-crossed

### Requirement 5: Quick Actions for Context Optimization

**User Story:** As a Kiro IDE user, I want quick actions that suggest starting a fresh conversation or switching steering files to more efficient inclusion modes, so that I can reduce context consumption with minimal effort.

#### Acceptance Criteria

1. WHEN the 80% threshold warning is shown, THE Extension SHALL include a "Start Fresh Conversation" action that opens a new Kiro chat session
2. WHEN the user invokes the "Optimize Context" command, THE Analyzer SHALL identify steering files set to `always` that could use `fileMatch` based on their tags and the workspace file patterns
3. WHEN the Analyzer identifies optimization candidates, THE Extension SHALL present a quick pick list showing each candidate with its current token cost and the recommended inclusion mode
4. WHEN the user selects candidates from the quick pick list, THE Extension SHALL apply the recommended inclusion mode changes to the selected files
5. WHEN a steering file contains language-specific tags (e.g., "typescript", "python"), THE Analyzer SHALL recommend `fileMatch` with an appropriate glob pattern (e.g., `**/*.ts` for typescript)

### Requirement 6: Active vs Dormant File Classification

**User Story:** As a Kiro IDE user, I want to see which steering files are currently active versus dormant, so that I understand exactly what is consuming my context window right now.

#### Acceptance Criteria

1. THE Classifier SHALL mark a steering file as active WHEN its inclusion mode is `always`
2. THE Classifier SHALL mark a steering file as active WHEN its inclusion mode is `fileMatch` AND at least one open editor file matches the `fileMatchPattern` glob
3. THE Classifier SHALL mark a steering file as dormant WHEN its inclusion mode is `manual`
4. THE Classifier SHALL mark a steering file as dormant WHEN its inclusion mode is `fileMatch` AND no open editor file matches the `fileMatchPattern` glob
5. WHEN the user opens or closes an editor tab, THE Classifier SHALL re-evaluate all `fileMatch` steering files and update their active/dormant status

### Requirement 7: Configuration

**User Story:** As a Kiro IDE user, I want to configure the context budget threshold and warning preferences, so that the extension adapts to my workflow and context window size.

#### Acceptance Criteria

1. THE Extension SHALL provide a `contextManager.contextBudget` setting with a default value of 32000 tokens
2. THE Extension SHALL provide a `contextManager.warningThresholds` setting with default values of 50% and 80%
3. THE Extension SHALL provide a `contextManager.enableWarnings` setting with a default value of `true`
4. WHEN the user modifies any configuration setting, THE Extension SHALL apply the changes immediately without requiring a reload

### Requirement 8: Workspace Context Estimation Beyond Steering Files

**User Story:** As a Kiro IDE user, I want the extension to estimate context consumption from sources beyond steering files (such as open editor files, spec documents, and workspace rules), so that I get a more complete picture of what is filling my context window.

#### Acceptance Criteria

1. WHEN the user invokes the "Show Context Breakdown" command, THE Estimator SHALL calculate estimated token counts for: active steering files, open editor files, and any `.kiro/specs/` documents in the workspace
2. WHEN displaying the context breakdown, THE Extension SHALL present a quick pick or informational panel showing each category with its estimated token count and percentage of the Context_Budget
3. THE Estimator SHALL calculate open editor file token costs using the same 4-characters-per-token heuristic applied to the file content length
4. THE Estimator SHALL clearly label all estimates as approximate with a disclaimer that actual Kiro context usage may differ

### Requirement 9: Alternative Approach Recommendations

**User Story:** As a Kiro IDE user, I want the extension to recommend alternative approaches like skills and knowledge bases when my steering files are too large, so that I can reduce context consumption by using on-demand loading instead of always-on steering.

#### Acceptance Criteria

1. WHEN a steering file set to `always` exceeds 2000 estimated tokens, THE Analyzer SHALL flag it as a candidate for conversion to a knowledge base or skill
2. WHEN the Analyzer flags a large steering file, THE Extension SHALL display a recommendation suggesting the user consider moving reference-heavy content to a Kiro knowledge base that only consumes tokens when searched
3. WHEN the "Optimize Context" command is invoked, THE Analyzer SHALL include knowledge base and skill recommendations alongside inclusion mode recommendations
4. THE Analyzer SHALL distinguish between behavioral guidance (suitable for steering files) and reference material (suitable for knowledge bases) based on file size and tag heuristics

### Requirement 10: Frontmatter Parsing and Serialization

**User Story:** As a developer, I want the extension to correctly parse and update steering file frontmatter, so that inclusion mode changes preserve the existing file content and formatting.

#### Acceptance Criteria

1. WHEN reading a steering file, THE Parser SHALL extract YAML frontmatter delimited by `---` markers and return both the frontmatter object and the markdown body
2. WHEN writing an inclusion mode change, THE Serializer SHALL update only the `inclusion` and `fileMatchPattern` fields while preserving all other frontmatter fields and the markdown body
3. FOR ALL valid steering files, parsing then serializing SHALL produce a file that re-parses to an equivalent frontmatter object and identical markdown body (round-trip property)
4. IF a steering file contains no frontmatter delimiters, THEN THE Parser SHALL return an empty frontmatter object and the full content as the body
